# Version-Issues-Hub v0.0.0.1

[GitHub issue #1](https://github.com/vixttha/Version-Issues-Hub/issues/1) is the first issue version on the internal `v0.0.0` line. This checkpoint defines the workflow that Version-Issues-Hub will test on itself. It is a design draft. The product has no active merge gate yet.

## What the first checkpoint delivers

- A record format and worked example that a human or VIB can follow from a GitHub issue.
- A repeatable public-runner pilot plan with positive and negative controls.
- The [Provenistem catalog](https://github.com/vixttha/Version-Issues-Hub/tree/Provenistem) links the ideas behind these decisions to planned capabilities and observable acceptance criteria.

## Version and evidence record

Assign the next unused positive integer on the selected `v0.0.x` line when Head accepts an issue into scope. Store the issue's repository and number separately from its version, such as issue #247 mapped to `v0.0.2.33`. Sorting and allocation compare the suffix numerically. The assigned number stays attached to the issue through retries and deferrals. Retain duplicate or retired assignments and link to the canonical issue. One PR can carry many records, and issues can share a fix commit when each has its own acceptance result.

| Field | Example for this checkpoint |
| --- | --- |
| Repository and GitHub issue | `vixttha/Version-Issues-Hub#1` |
| Development line and issue version | `v0.0.0`, `v0.0.0.1` |
| Acceptance | Review the contract and pilot cases in this document. |
| State | Draft for owner review. |
| Fix and tested revisions | Link the design commit and catalog workflow separately. The catalog checkout cannot verify the design's future enforcement. |
| Evidence | Record check name, effective checkout SHA, outcome, run URL and attempt. Record job and artifact identifiers when used. |
| Integration | Record PR and actual merged SHA after the owner's decision. |
| Product publication | Record a public-ready `v0.x` release only after the owner's decision. Public repository visibility is for runner access during development. |

Recommended lifecycle: assigned, in progress, verified, integrated. A blocked or deferred issue records its reason and next action. When a check reruns, preserve the older result and record the new attempt and checkout. Preserve the PR head, base and proposed merge checkout where they differ. A later handoff should be able to recover the scope, accepted record, latest tested revision and next action from GitHub without chat history.

## How VIB works

Head sets scope. One Worker makes the change. Validate reproduces the issue when possible, checks the repair, and records the evidence. Internal Auditor checks the diff against the issue and evidence. Head decides integration and publication. VIB is the workflow identity. GitHub rules and checks enforce protected-branch policy once the pilot proves it.

## What the enforcement pilot must prove

Use standard GitHub-hosted runners in a disposable public repository or a disposable target branch. Keep the verifier policy and the trusted check publisher outside the candidate's control. Use a unique required check and require a candidate against the current base. Read back the active rules and the actual merge eligibility. A skipped required test should cause the policy verdict to fail.

| Case | Expected outcome |
| --- | --- |
| Correct batched PR | GitHub reports it eligible once the required validator succeeds and any other configured requirements pass. |
| Missing issue mapping or acceptance evidence | GitHub blocks the merge. |
| Duplicate assignment or changed historical mapping | GitHub blocks the merge. |
| Evidence for an old revision or a skipped required test | GitHub blocks the merge. |
| Repeated allocation request | It reuses the same mapping and reserves no additional number. |
| Fresh human or agent handoff | Finds the exact issue, source, latest evidence, current blocker and authorized next action. |

Start with a Git-backed ledger and one writer. A trusted GitHub App, enforcement on an adopter's main branch, automated installation beyond the current catalog, and release publishing are later implementation decisions. Notion can show the handoff. CodeRabbit can review future diffs. External CI can supply evidence through the same record format if needed. The pilot uses GitHub Actions as its execution path.
