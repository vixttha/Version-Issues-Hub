# v0.0.0.40 — Issue closure synchronization (#86)

## Independent lifecycle states

Inspect reports engineering completion (recorded or unverified), GitHub issue state/reason, canonical production integration and closure synchronization separately. A closed issue does not imply production integration. Historical closed records without a closure receipt remain historical_unverified; no bulk changes. A recorded engineering receipt is not a fresh verification verdict.

## Owner-reviewed closure

Use a reviewed policy file: schema_version 1, repository, issue, version, archive_ref (immutable installed revision containing the disposition), archive_digest (SHA-256 of install.render of the exact archive), reason, owner_decision, engineering (the .39 engineering policy envelope, or null for already-closed not_planned). Legacy engineering decisions require an explicit owner-reviewed complete policy and verified exact merge, run/attempt, job and criteria evidence; the exact archived PR, fix, candidate and merge pins must match; free-form prose is not itself proof. For recorded .39 structured evidence require exact equality. Only inactive deferred engineering issues are eligible; already-closed matching not_planned deferred/blocked issues can be reconciled. Staged, active and experimental/release-held self-use issues #37/#40/#53 are not eligible. No new not_planned closure or automatic reopen. No universal inference of owner intent or proof of authorization from GitHub state alone.

Use the reviewed package and exact current installed ref:

- `python -m tools.session --target OWNER/REPO --expected-sha CURRENT issue-closure NUMBER --stage prepare --policy FILE --owner-approved`
- After review, append `--apply` to publish the pending intent. Read back the new installed ref.
- Repeat with `--stage complete` and the new exact current installed ref; dry run first, then explicitly apply.

The canonical pending and confirmed receipts append to history, preserving the original disposition and mapping. Only one pending closure is allowed; pending blocks new claims. Issue PATCH and ledger ref publication are separate operations; a crash or ambiguous response leaves intent for owner reconciliation. Reload issue and installed SHA, inspect outcome, never blindly repeat an ambiguous PATCH. Reapply only after determining whether the issue is still open, closed for the expected reason, or conflicting. Confirmation requires matching GitHub readback, reverified historical evidence, and current lease. Both intent and confirmation publications verify the serialized ledger and handoff blobs at the returned exact revision. No automatic retries or atomic cross-API claims. Cooperative authorization, not an access-control guarantee. A concurrent direct GitHub issue edit can still race the final readback.

Reserved closure decision prefix requires collision review before migrating any older installation. Older readers do not understand closure records; the operation refuses an installed package without the closure capability; use a reviewed compatible package after owner authorization. No actual migration or issue closure in this checkpoint. Existing production path remains independent. Ordinary fixture regressions only.
