# v0.0.0.40 — Issue closure synchronization (#86)

## Independent lifecycle states

Inspect reports engineering completion (recorded or unverified), GitHub issue state/reason, canonical production integration and closure synchronization separately. A closed issue does not imply production integration. Historical closed records without a closure receipt remain historical_unverified; no bulk changes. A recorded engineering receipt is not a fresh verification verdict.

## Owner-reviewed closure

Use a reviewed policy file: schema_version 1, repository, issue, version, archive_ref (immutable installed revision containing the disposition), archive_digest (SHA-256 of install.render of the exact archive), reason, owner_decision, engineering (the .39 engineering policy envelope, or null for already-closed not_planned). Legacy engineering decisions require an explicit owner-reviewed complete policy and verified exact merge, run/attempt, job and criteria evidence; the exact archived PR, fix, candidate and merge pins must match; every populated archived handoff PR, fix and candidate pin must also equal the policy, even when the decision cites multiple PRs. Free-form prose is not itself proof. For recorded .39 structured evidence require exact equality. Only inactive deferred engineering issues are eligible; already-closed matching not_planned deferred/blocked issues can be reconciled. Staged, active and experimental/release-held self-use issues #37/#40/#53 are not eligible. No new not_planned closure or automatic reopen. No universal inference of owner intent or proof of authorization from GitHub state alone.

Use the reviewed package and exact current installed ref:

- `python -m tools.session --target OWNER/REPO --expected-sha CURRENT issue-closure NUMBER --stage prepare --policy FILE --owner-approved`
- After review, append `--apply` to publish the pending intent. Read back the new installed ref.
- Repeat with `--stage complete` and the new exact current installed ref; dry run first, then explicitly apply.

The canonical pending and confirmed receipts append to history, preserving the original disposition and mapping. Only one pending closure is allowed; pending blocks new claims. Unscoped inspect exposes its issue, version, policy and archive digests and reconciliation status. Confirmed status additionally requires the current inactive ledger disposition to match the archived basis. Issue PATCH and ledger ref publication are separate operations; a crash or ambiguous response leaves intent for owner reconciliation. Reload issue and installed SHA, inspect outcome, never blindly repeat an ambiguous PATCH. Never replay an executing intent after a lost response. Inspect the exact execution receipt and current issue state; owner recovery requires a stopped executor and the exact execution ID. Confirmation requires matching GitHub readback, reverified historical evidence, and current lease. Both intent and confirmation publications verify the serialized ledger and handoff blobs at the returned exact revision. No automatic retries or atomic cross-API claims. Cooperative authorization, not an access-control guarantee. A concurrent direct GitHub issue edit can still race the final readback.

Reserved closure decision prefix requires collision review before migrating any older installation. Older readers do not understand closure records; the operation refuses an installed package without the closure capability; use a reviewed compatible package after owner authorization. No actual migration or issue closure in this checkpoint. Existing production path remains independent. Ordinary fixture regressions only.

## Cancel an unrecoverable closure intent

When evidence is stale or a live issue conflicts, the owner may abandon the exact pending intent without confirming or changing the GitHub issue. First ensure no closure process or direct issue mutation is in flight; GitHub provides no atomic cross-API lock. Reload the current ref and issue, then use `issue-closure NUMBER --stage cancel --policy ORIGINAL_FILE --decision "Owner decision and confirmation no concurrent closure execution" --owner-approved` with global `--expected-sha CURRENT`; review dry run, then apply. Cancellation verifies current installed lease, exact pending policy and archive, records observed state/reason and appends a terminal cancelled receipt. It deliberately does not revalidate stale workflow proof, PATCH an issue, or assert successful closure. Original intent and historical mappings remain intact. A cancelled intent cannot be replayed; a new closure requires a distinct owner-reviewed policy and all normal proof. A structured engineering policy whose workflow evidence can no longer pass remains ineligible until separately reconciled; cancellation releases the lane without certifying it. Cancellation is idempotent for the same recorded decision. Do not use cancellation concurrently with a completion invocation; cooperative owner serialization remains required.

## Red Team pre-push hardening (RT-001, RT-004, RT-005, RT-008)

An applying completion first publishes a unique executing receipt against the exact pending revision using non-force fast-forward publication. Only the invocation that acquired an unambiguous publication response and read back the exact current execution revision proceeds to issue mutation. Even a recovered ambiguous acquisition response requires owner reconciliation before any issue mutation. Competing completion/cancellation from the old parent must fail; an executing intent is never automatically replayed. Owner recovery requires the exact execution ID via `--stage cancel --recover-execution ID --decision TEXT --owner-approved`, with the original policy and current lease, after stopping the original executor and reconciling live state. Ordinary cancellation cannot cancel an executing intent. This is cooperative serialization; direct writers and an owner who falsely attests that an executor stopped can still race GitHub's independent issue API. No atomicity or independently authenticated owner claim.

A confirmed historical receipt now reports `state_matches_historical_receipt` when current state/reason and canonical disposition match. `closure_event_verified` is always false: reopening and reclosing for the same reason cannot be distinguished from the original event using issue state alone. Historical receipt and current state are reported separately. Lifecycle upgrade and retirement preparation reject any pending or executing intent. Package compatibility rejects reserved-prefix history on packages lacking the reviewed execution marker; do not reinterpret legacy prose or downgrade a receipt-aware package without qualification.

Owner approval authentication (RT-002/011) stays on .41, broader evidence reuse (RT-006) on .42; live installed upgrade (RT-003), historical archive graph backfill (RT-007), cumulative evidence (RT-010), independent trials and release remain separate held gates.
